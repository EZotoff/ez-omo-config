Infrastructure recap

OpenCode on Android: built, secured, one action from verified

How coding sessions on ez-raider (the Linux workstation) became reachable from an Android phone — and what is still open.

Date: 2026-09-05 · Scope: workstation + tailnet setup · Client: OC Beacon 0.3.0 · Audience: the owner, months later

The result: a dedicated OpenCode server now runs on ez-raider as a boot-enabled service, reachable only through the private Tailscale network with real TLS encryption and password authentication. The Android app (OC Beacon) is installed on the phone (nothing-phone-2). One action remains: the app's server address must be changed to the https:// URL below — the http:// address entered first no longer exists. That connection is also the acceptance test: once one session runs from the phone, the last open decision — retiring the old mobile solution (OpenChamber) — can be taken.

Why this exists

Previously, every project directory ran its own separate opencode process inside a Zellij pane (Zellij is a terminal multiplexer; its panes are the workstation's split terminal windows). Those processes die with their pane and are invisible to any other device — a phone can only talk to an OpenCode server that listens on the network. A second, older mobile access route (OpenChamber, a Telegram-facing bot on port 3021) already existed but is now slated for retirement once the new path proves itself.

The occasion was a Gemini-generated PDF recommending an Android setup. Its architecture advice was correct; its literal commands were not safe to follow (details below). This recap documents both the critique and what was actually built instead.

What was assessed

The advice PDF: right architecture, unsafe commands

The PDF recommended one central opencode serve daemon plus lightweight attached terminals, accessed from Android over Tailscale — and that architecture is genuinely how OpenCode (v1.18.5, the installed version) is designed to work. Every command it cited was verified against the live binary and exists.

Its instructions had one dangerous gap: they said to bind the server to 0.0.0.0 — every network interface, LAN included — with no password. An OpenCode server API can execute shell commands and edit files; unauthenticated, it is a remote-code-execution endpoint for anything that can reach the port. The setup below deliberately does the opposite: loopback-only binding, TLS, and a password.

The Android app (OC Beacon): audited, fit for purpose

OC Beacon is a community fork of an existing Android client called OC Remote (the original open-source app this one builds on; Kotlin, MIT licence, actively maintained — last code push four days before this setup). A static source review — the code was read line by line, but the app was not run — found the quality unusually high for a solo project and no security defects in the code paths examined. Measured, not assumed:

  • Server passwords and the GitHub login token are encrypted with the Android hardware keystore (AES/GCM) and excluded from cloud backups and device transfers.
  • Crash logs are scrubbed of credentials, tokens, IP addresses, and file paths before anything leaves the device; no advertising or tracking libraries are present anywhere.
  • In-app updates verify both a SHA-256 checksum and the developer's signing certificate before installing.

Three informed trade-offs were accepted (documented in the project, not hidden): it allows plain-HTTP server addresses by design (irrelevant here — this setup is HTTPS); a GitHub client secret is compiled into the app (low impact on its own); and the optional bug-report feature attaches logs to a semi-public gist (off by default, user-initiated).

The app version installed is the official signed release 0.3.0 — chosen over a custom build so the app's own update mechanism keeps working across future releases.

What was built

A second OpenCode server, dedicated to mobile and interactive work

A new systemd user service, opencode-interactive.service, runs opencode serve on port 3030, bound to 127.0.0.1 only. It starts at boot, restarts on failure, and is completely independent of the OpenChamber service — a crash or restart of one cannot touch the other. Desktop terminals can attach to it later with opencode attach http://127.0.0.1:3030 --dir <project> to get the same pane-immortality the phone gets; existing habits need no change until then.

Safe exposure to the phone

The OpenCode API is never bound to a physical network interface. Instead, Tailscale's built-in reverse proxy publishes it inside the private tailnet at:

https://ez-raider.tailb8fd09.ts.net:3030

with a Let's Encrypt certificate (a real certificate authority, so the phone trusts it with no custom configuration). Access requires a username and password; the password is stored only in ~/.config/opencode/serve-interactive.env (permission 600, readable by the owner's account alone) and is deliberately not reproduced in this document. Devices must be members of the tailnet to see the address at all; the internet at large sees nothing.

Verified from the workstation on setup day: the address answers 401 (refused) without credentials and 200 (accepted) with them.

Leftovers removed

The machine previously published a Tailscale "Funnel" — a public-internet address — that forwarded to port 4400, where no service had been listening for some time. It was removed; the machine now exposes nothing to the public internet. Tailscale management was also switched to a non-root operator account (ezotoff), so future proxy changes no longer need administrator rights.
